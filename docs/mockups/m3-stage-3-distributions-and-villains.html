One thing in the brief isn't in Stage 3's criteria

Day-of-week and month tables are not built in this mockup, and shouldn't be built in this stage. The task brief asked for them, but docs/PRD.md's Stage 3 criteria block (223–249) contains no day-of-week or month criterion at all, and the spec says so explicitly twice: the "Explicitly out of scope for Stage 3" list names "Venue and date slices — Stage 4, per open question 9", and Stage 4's own scope line lists "day-of-week and time-of-year" cuts by name. Criteria 193 and 246 require every fixed string this stage ships to trace to a numbered criterion — there is no criterion number for a day/month table to trace to, so adding one here would be inventing scope the PRD deliberately deferred, not designing what was asked for. This mockup builds everything Stage 3 actually specs — the board's five new cards, the player and roster page additions, and the /stats catalogue (trend, villains table, disasters list, averages) — and leaves day-of-week/month tables for Stage 4's own mockup, when its criteria are written. Flagging this now is cheaper than building a component against a criterion number that doesn't exist and finding out at QA.

The legibility call (open question 12): twelve cards at 375px is roughly two and a half screens of scrolling — noticeably more than Stage 2's seven, which already put the newest two records below the fold. Nothing here is designed to hide that: no accordion, no "show more" collapse, no tab switcher splitting the board in two — the founder's own default was "build all twelve," and a collapsed board would quietly reintroduce the withholding the founder explicitly rejected at Stage 1 (open question 6), just spatially instead of numerically. What the layout does do: grouping Stage 3's five cards as a contiguous block at the bottom means a reader who only cares "what's new since last week" can stop scrolling once the outlined block ends, and the founder's original four are still the first thing on screen, unscrolled, at every viewport. If this still doesn't read as five seconds' worth on your phone, the fix is exactly what criterion 235's note says: cut or reorder a row, which costs one deletion, not a rebuild.
No caveat beyond the sample statement (open question 3a, answered): the five new cards carry no warning icon, no "read carefully" line, no different tone from the other seven — the founder's 2026-09-14 answer was explicit that nothing is added beyond the existing sample pattern, and criterion 233 only changes what the sample says (a date, not a game count), never adds a second sentence on top of it. ArchiveLine's early-days line is unchanged and still governs the whole board, not these five cards specifically.

Criteria 228, 230–231, 233 — a new RecordCard variant

Tied single-event cards read as a list of instances, not a list of names

Every existing joint-holder rule (criterion 181) lists names against one shared number — "Player A & Player E, 4." That grammar breaks for these five records, because criteria 228, 230 and 231 all specify the same unusual case: the same player can hold the record twice, in two different games (or, for the catastrophe, two different hands). A flat name list can't say that — "Player D" once is one fact; "Player D" listed twice, each with its own date, is a different fact, and the card has to be able to state it.

The rule: when a single-event record has exactly one instance (the ordinary case — see every other card on the board above), it renders like any other RecordCard: holder name, then the date line in place of "from {n} games." When it has more than one instance, the holder line is replaced by a stacked list of instance rows — one per (player, game) pair, each with its own date — under the single shared number, which by definition is identical across every instance (that's what makes them tied). The catastrophe's instance rows add the hand, since two tied instances can be on different hands: "Player B — Kings, Sat 15 Aug 2026".

Criteria 233–234 — the date-based drill-through

Drill-through: "Worst game ever" — a date, not a game count

This is the one deliberately shown in full: every other drill-through on this board states its claim as "from {n} games" — this one, and its four siblings, state the date the game was played instead, because the record is one observation, not a rate over a history (criterion 233). The list below it is Stage 1's unmodified drill-through pattern (criterion 186) reused exactly — and here it is, correctly, a single row (decision 24): one event, one game, nothing padded in to make the list look fuller than it is.
