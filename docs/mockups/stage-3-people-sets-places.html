People, sets and places

Milestone 2 Stage 3 mockups — players, rosters and places, renaming, and the new navigation that ties them into the record (PRD criteria 132–146, 174). Matches docs/DESIGN-SYSTEM.md's existing Kitchen Table language exactly: same tokens, same components, nothing reinvented. Purple dashed boxes are designer annotations, not app UI.

Design decisions to approve

  1. Where the three index pages hang off the games list — a new IndexNav row (Players / Rosters / Places) directly under the games list's "Add a game" button, always visible.
  2. Roster names become links wherever they appear outside their own page — games list rows, game view, and player pages — styled as underlined brand-coloured text (an EntityLink), never colour alone.
  3. Player names become links only on the game view's "How it finished" list (not also in the score table's column headers), to keep the dense score grid's tab order simple.
  4. A game-list row stays one large tap target to open the game, with the roster name as a second, independently-tappable link layered on top (a "stretched link" pattern) — nobody loses the big, easy row they have today.
  5. Roster renaming lives inline on the roster page itself, behind a "Rename" link that reveals a field — no separate screen. Location renaming lives inline on the places index, per-row, the same shape.
  6. No "place page." The PRD only asks for a places index; there's nowhere else for a location to link to yet, so places-index rows aren't links at all, just name + count + a rename control.
