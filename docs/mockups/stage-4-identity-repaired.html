Milestone 2 Stage 4 mockups — the suggested player match's pre-selected state, merging two players, and merging two places (PRD criteria 148–166, 172–173). Matches docs/DESIGN-SYSTEM.md's existing Kitchen Table language exactly: same tokens, same components, nothing reinvented. Purple dashed boxes are designer annotations, not app UI.

Design decisions to approve

  1. A pre-selected suggestion gets exactly one new signal: a small neutral "Suggested" Pill beside the column's player name, cleared the instant the founder touches that column's name control. No new pager-dot state, no colour change, no extra tap anywhere — it's already accepted (criterion 172).
  2. The handwritten name now stays visible on every column, not only unmatched ones — a small muted "Read as …" line under the player's name, always present once a transcription exists (criterion 153). This is the one change that touches every column, not just suggested ones.
  3. A near-match or ambiguous column stays unassigned, exactly like today's M1 pick-list, except its PickList sheet now opens with a "Closest matches" section pinned above the full roster (criterion 173) — no new component, an ordering change to the existing one.
  4. Both merges are reached from where they're needed: player merge from "This is the same person as…" on the player page (both the populated and the zero-game layout), place merge from the places index. Both use one confirmation screen — arriving there is the first deliberate action, tapping Merge permanently is the second — the same two-step shape "Deleting a game" already established.
  5. The same-game refusal is a dead end by design: no survivor picker renders at all when the two players share a game. Just the conflict, named games with edit links, and the way back. Nothing is chosen until the conflict is gone.
  6. Place merge's hard problem — the entry point stays off PlaceRow's pencil button, not a second icon. Tapping the pencil now opens a two-row chooser ("Rename" / "Merge with another place…") in the same "reveal in place" slot the row already uses for renaming — the row itself is pixel-identical to Stage 3 at rest. The rename-collision refusal gets a direct "Merge with {existing place}" button, since at that point both places are already known and asking again would be busywork.

Review screen — a confident suggestion

Criteria 148, 150, 152–154, 172. ≥0.80 similarity with a clear leader: the player is already selected when the screen first renders. Zero taps to save.

Review screen — no confident match

Criteria 149, 151, 173. A near match (0.55–0.80), an ambiguous tie within 0.10, or nothing plausible at all (<0.55, or an empty player list) — all three render identically: no player selected, save blocked on this column exactly as M1 already blocks an unassigned one.

Player page — the merge entry point

Criterion 155. Reached from a player's own page, available to anyone with the group password. Present on both layouts — a zero-game player is exactly the duplicate most likely to need merging away, so the empty state carries the link too.

Merge — pick who to merge with

Tapping "This is the same person as…" opens a sheet in the same shape as every other picker in this app — no "add new" row here, since there's no "someone new" concept for a merge target.

Design call: reused PickList's row shape rather than invent a second list idiom, with each row's games-played count as secondary text (an existing duplicate is often the one with almost no games) — and no add-new footer, since it doesn't apply.

Merge — confirmation

Criteria 156–157. Names both, shows each one's games played, and the founder explicitly picks the survivor — nothing defaults by age or size. Arriving here is the first deliberate action; tapping "Merge permanently" is the second, same shape as "Deleting a game".

Merge — the same-game refusal

Criterion 160. Where both players appear in the same game, the merge is refused before anything changes — so there is nothing to pick a survivor for yet. Every offending game is named with a link to edit it.

Design call: this replaces the whole survivor-picker — not a banner sitting above a still-enabled one. There is genuinely nothing safe to offer until the conflict is gone, so nothing resembling a choice renders at all.

Merge — after it runs

Criterion 161–162. Redirects to the survivor's own page; the losing player's page and URL now 404. No screen anywhere mentions that a merge happened, beyond this one-time banner.

Places index — rename or merge

Criterion 163. PlaceRow is already fully-loaded at 375px: name, an optional caption, a right-aligned count, and one 44×44 pencil button. The merge entry point has to live somewhere on this row without crowding it.

Design call: no second icon button, no overflow menu. The pencil now opens a small two-row chooser in the exact spot the row already reveals its rename field — the row is pixel-identical to Stage 3 until it's tapped. Its aria-label changes from "Rename {place}" to "Edit {place}", since the pencil no longer commits to one action.

Merge places — confirmation

Criteria 163–166. Same mechanism and permanence wording as a player merge. No same-game refusal applies here — a game has exactly one location, so two places can never both be "in the same game" the way two players can.

Rename collision — now offering the merge

Criterion 163 fulfils criterion 146's promise: the refusal screen said "coming in a later update" in Stage 3. This is that update.

Design call: a direct "Merge with {existing place}" button under the refusal, not a trip back through the picker sheet — both places are already known at this exact moment, so re-asking "which place?" would be busywork the founder just did by typing the name.
